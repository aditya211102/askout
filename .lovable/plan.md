# Lovable Coupling Audit — Askout Moments

Read-only inventory. Nothing was modified.

## Verdict

This repo is a plain Vite + React + TypeScript app talking to a Supabase project. The only build-time Lovable code is one dev dependency (`lovable-tagger`). Everything user-facing (auth, database, storage, edge functions, payments) runs on Supabase and Dodo Payments, which keep working after you leave Lovable — as long as you keep access to the Supabase project itself.

No `lovable` imports exist anywhere in `src/`. No Lovable SDK, no Lovable AI Gateway calls in application code (`LOVABLE_API_KEY` exists as a backend secret but no function reads it).

## 2. `.lovable` and workspace files

- `.lovable/plan.md` — planning scratch file, no runtime role.
- `.workspace/` — Lovable-managed skills mount, not part of the app.
- Neither is imported by the build. Both are safe to delete after migration.

## 3. Backend usage (Lovable Cloud)

The backend is a Supabase project provisioned through Lovable Cloud. In-repo footprint:

- `supabase/config.toml` — project ref + `verify_jwt = false` for `dodo-webhook` and `create-checkout`.
- `supabase/migrations/` — 6 SQL migrations (schema, RLS, storage).
- `supabase/functions/create-checkout` and `dodo-webhook` — Deno edge functions.
- Client: `src/integrations/supabase/client.ts` (auto-generated by Lovable, reads `VITE_SUPABASE_*` env vars) and `src/integrations/supabase/types.ts`.

Important: the Supabase project is *provisioned and billed* through Lovable Cloud. The code is portable; the project ownership is the one real dependency. Confirm with Lovable support whether the Cloud-provisioned Supabase project can be transferred to your own Supabase org, or plan to recreate it (migrations + storage buckets + secrets) in a self-owned Supabase project and re-point the env vars.

## 5. Hosting/deployment assumptions

The repo is already configured for Vercel, not Lovable hosting:

- `vercel.json` with SPA rewrites — correct for Vercel.
- `index.html` canonical/OG URLs and `src/lib/site.ts` `SITE_URL` all point at `https://askout-moments.vercel.app`.
- `public/sitemap.xml` and `public/robots.txt` should be checked for the same domain.
- Lovable's published URL `askout.lovable.app` stops resolving when you stop publishing from Lovable; anything linking to it (including PRD docs and any external backlinks) breaks.

## 6. What breaks on a standalone GitHub + Vercel deploy

1. **Env vars.** `.env` is git-ignored, so `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_PROJECT_ID` are not in the repo. Without setting these in Vercel the app builds but every backend call fails at runtime.
2. **Backend secrets.** `DODO_*`, `SUPABASE_SERVICE_ROLE_KEY`, etc. live in the Supabase project, not the repo. They survive if the project survives; they must be re-created if you rebuild the project.
3. **Edge function deploys.** Lovable deploys them today. Standalone you need the Supabase CLI (`supabase functions deploy`) and to re-apply `verify_jwt = false` for both functions.
4. **Migrations.** No automatic apply outside Lovable — run `supabase db push` yourself.
5. **Auth redirect URLs.** Supabase Auth's Site URL / allowed redirect list currently includes the Lovable preview and `askout.lovable.app`. Add your Vercel/custom domain or sign-up confirmation and OAuth redirects break.
6. **Storage buckets** `voice-notes` and `voice-backgrounds` must exist in whichever Supabase project you point at.
7. **Auto-generated files** (`src/integrations/supabase/client.ts`, `types.ts`) stop regenerating; you maintain them (`supabase gen types typescript`).
8. **Dodo webhook URL** points at the current Supabase functions domain — must be updated if the project changes.

## Migration checklist

1. Decide the Supabase project's fate: transfer ownership, or create a self-owned project and apply `supabase/migrations`, recreate the two storage buckets, and re-add all secrets.
2. Set `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_PROJECT_ID` in Vercel (all environments).
3. Link the repo to Vercel; build command `npm run build`, output `dist`. `vercel.json` already handles SPA routing.
4. Install the Supabase CLI locally; `supabase link`, `supabase db push`, `supabase functions deploy create-checkout dodo-webhook`.
5. Update Supabase Auth Site URL + redirect allowlist to the production domain; remove Lovable preview URLs.
6. Update the Dodo Payments webhook endpoint and confirm live/test mode via `DODO_LIVE_MODE`.
7. Confirm `index.html`, `src/lib/site.ts`, `public/sitemap.xml`, `public/robots.txt` all use the final production domain.
8. Smoke test end to end: sign up, create each product type, checkout, webhook marks card paid, viewer pages load.

## Safe to remove (only after migrating)

- `lovable-tagger` dependency and the `componentTagger()` plugin + import in `vite.config.ts`.
- `.lovable/` and `.workspace/` directories.
- `README.md` Lovable sections (replace with your own setup docs).
- `docs/PRD.md` references to `askout.lovable.app` and "Lovable Cloud".

## Do NOT remove

- `supabase/` (config, migrations, functions) — this is your backend.
- `src/integrations/supabase/*` — even though marked auto-generated, the app imports it.
- `vercel.json`, `@vercel/analytics`, all env-var usage.
